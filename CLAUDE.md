# Проект: Фактуриращо бизнес приложение

## Цел на приложението
Уеб приложение за издаване на фактури и съхранение на свързаните данни. Основни функционалности:
- Издаване на фактури с автоматична последователна номерация
- Настройки на фирмата, която ползва приложението (име, ЕИК, ДДС регистрация)
- Управление на контрагенти (клиенти/доставчици)
- Управление на продукти/услуги
- История и справки по издадени фактури

## Технологичен стек

### Backend
- **Python 3.11+**
- **FastAPI** — REST API framework
- **SQLAlchemy** — ORM
- **Alembic** — версionирани миграции на схемата
- **Pydantic** — валидация на входните данни

### База данни
- **Старт: SQLite** — за локална разработка
- **Цел: PostgreSQL** — за production hosting
- Схемата се пише и мигрира през SQLAlchemy + Alembic по начин, който е агностичен към конкретния database engine (виж `docs/ARCHITECTURE.md` за детайли и правила какво да се избягва)

### Frontend
- **React** + **TypeScript**
- **Vite** — build tool
- Комуникация с backend-а през REST API (JSON)

## Ключови бизнес правила
- Веднъж издадена фактура **не се редактира ретроактивно** — данните за фирмата, контрагента и продуктите се "снимат" (denormalize) в самата фактура към момента на издаване.
- Номерът на фактурата е **последователен, без прекъсвания и без дублиране** — критично за счетоводна валидност.
- Паричните суми **винаги** се обработват като `Decimal`, никога като `float`.
- Ако фирмата не е регистрирана по ДДС, фактурата трябва да съдържа текстово основание за неначисляване на ДДС (конфигурируемо в настройките на фирмата).

## Конвенции при разработка
- Backend и frontend са отделни папки/проекти в рамките на repo-то (виж `docs/ARCHITECTURE.md` за структура).
- Всяка промяна в модела на данните минава през Alembic migration — не се редактира схемата директно в базата.
- Кодът предпочита яснота пред краткост — това е счетоводен/финансов софтуер, грешките имат реална цена.
